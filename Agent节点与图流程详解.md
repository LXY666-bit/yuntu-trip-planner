# 云途(YUNTU) Agent 节点与图流程深度详解

> 本文档逐一拆解项目中所有的 Agent 节点和三套有向图流程，包含每个节点的输入/输出、内部逻辑和节点间流转关系。

---

## 一、节点全景图：4 张图 × 27 个功能节点

项目实际包含 **4 张 LangGraph 有向图**，其中 3 张面向用户场景，1 张作为可复用的嵌套子图：

| 图名 | 函数 | 用途 | 节点数 |
|------|------|------|--------|
| **主规划图** | `create_trip_planner_graph()` | 全自动端到端旅行规划 | 17 |
| **景点发现图** | `create_discovery_graph()` | 大量搜索景点供用户选择 | 6 |
| **自选规划图** | `create_planning_graph()` | 基于用户已选景点直接生成行程 | 10 |
| **单日详情子图** | `_create_day_plan_subgraph()` | 被主图和自选图嵌套调用，并行生成每日详情 | 5 |

#### 关键设计决策

**三段并行启动** — 节点 ①④⑤ 同时从 START 出发：
```python
workflow.add_edge(START, "web_search_attractions")  # 搜索景点攻略
workflow.add_edge(START, "search_weather")           # 查询天气
workflow.add_edge(START, "search_hotel")             # 搜索酒店
```
这三个任务互不依赖，并行执行可以将此阶段耗时缩短到最慢任务的时长。

**三路汇聚** — 节点 ③④⑤ 都完成后才进入 gather_search：
```python
workflow.add_edge(["geocode_attractions", "search_weather", "search_hotel"], "gather_search")
```
这确保聚类节点启动时，景点坐标、天气、酒店三项数据齐全。

**条件路由** — gather_search 根据错误情况分流：
```python
workflow.add_conditional_edges("gather_search", _route_after_gather, {
    "cluster_attractions": "cluster_attractions",  # 正常路径
    "error_handler": "error_handler",              # 有致命错误
})
```

**Send API MapReduce** — macro_planner 完成后动态派发 N 个并行子图：
```python
def _route_to_day_plans(state) -> List[Send]:
    sends = []
    for day_skeleton in macro_plan.days:
        sends.append(Send("day_plan_subgraph", {
            "day_index": day_skeleton.day_index,
            "date": day_skeleton.date,
            "attraction_names": day_skeleton.attraction_names,
            "hotel_name": day_skeleton.hotel_name,
            ...
        }))
    return sends
```

### 2.2 景点发现图 `create_discovery_graph()` — 交互式景点选择

**场景**：用户想先看到系统搜出来的所有景点，手动勾选感兴趣的分天安排，再进入规划。

```
                         ┌──────────────┐
                         │    START     │
                         └──┬────────┬──┘
                            │        │
                  ┌─────────▼──┐ ┌──▼───────────┐
                  │ ① web_     │ │ ⑤ search_    │  ← 天气与搜索并行
                  │ search_    │ │ weather      │
                  │ attractions│ └──────┬───────┘
                  └─────┬──────┘        │
                        │               │
                  ┌─────▼──────────┐    │
                  │ ② extract_     │    │
                  │ attractions_   │    │  ← 扩展版：提取20-40个景点
                  │ expanded       │    │
                  └─────┬──────────┘    │
                        │               │
                  ┌─────▼──────┐        │
                  │ ③ geocode_ │        │
                  │ dispatch   │        │  ← 将景点分成每批5个
                  └─────┬──────┘        │
                        │               │
                  ┌─────▼──────┐        │
                  │ ④ geocode_ │◄──┐    │  ← 循环处理每一批
                  │ batch      │──┘    │     (有剩余批次时自循环)
                  └─────┬──────┘        │
                        │               │
                        └───────┬───────┘
                                │
                       ┌────────▼────────┐
                       │ ⑥ gather_       │
                       │ discovery       │  ← 统计汇总，输出到前端
                       └────────┬────────┘
                                │
                       ┌────────▼────────┐
                       │      END        │
                       └─────────────────┘
```

#### 与主规划图的关键区别

| 对比点 | 主规划图 | 发现图 |
|--------|---------|--------|
| 景点提取数量 | 3×天数（3天≈9个） | 最多40个（6×天数） |
| 地理编码方式 | 一次性全部编码 | **分批**（每批5个），每批完成后立即 SSE 推送给前端 |
| 下游节点 | 直接进入聚类→生成 | 停在 gather_discovery，等待用户选择 |
| 是否需要酒店/美食 | 是 | 否（只发现景点） |

**自循环批处理** — geocode_batch 的处理逻辑：
```python
def _route_after_geocode_batch(state) -> str:
    if state.get("_geocode_batches"):   # 还有剩余批次
        return "geocode_batch"           # 继续循环
    return "gather_discovery"            # 全部完成
```
每处理完一批（5个景点），就把结果通过 SSE 推送给前端，同时检查是否还有剩余批次。这样用户不用等所有景点都编码完就能看到第一批结果。

#### 与主规划图的关键区别

| 对比点 | 主规划图 | 自选规划图 |
|--------|---------|-----------|
| 入口数据 | 只有城市名，需要从零搜索 | 用户已提供景点名+坐标+日程分配 |
| 是否需要搜索景点 | 是（①→②→③） | **否**，跳过整个搜索链路 |

| 酒店搜索时机 | 与景点搜索并行（START→⑤） | 聚类完成后与美食、路线并行 |

### N1: `web_search_attractions_node`

```
┌─────────────────────────────────────────────────────────┐
│  输入                                                    │
│  ├─ state.request.city          : str   # 目标城市       │
│  ├─ state.request.travel_days   : int   # 旅行天数       │
│  ├─ state.request.preferences   : list  # 用户偏好标签   │
│  ├─ state.request.companions    : obj   # 同伴类型       │
│  ├─ state.request.budget        : float # 预算           │
│  └─ state.request.free_text_input: str  # 额外要求文本   │
├─────────────────────────────────────────────────────────┤
│  输出                                                    │
│  ├─ raw_search_results : str  # 所有搜索结果的拼接文本   │
│  └─ errors             : list # 错误信息（失败时）       │
├─────────────────────────────────────────────────────────┤
│  内部逻辑 (搜索策略)                                      │
│                                                          │
│  1. 构建搜索词列表 (根据天数/偏好/预算动态生成)           │
│     基础搜索词: "{city} 必去景点 top10"                   │
│                 "{city} 旅游攻略 必去"                    │
│                 "{city} 最值得去的景点"                   │
│     偏好搜索词: "{city} {偏好} {同伴} 景点推荐"           │
│     预算搜索词: "{city} 免费景点" (预算<3000时)          │
│                                                          │
│  2. 主搜索 (并行): 小红书游记 + 必应 MCP                  │
│     ├─ 小红书: 搜索真实游记，LLM 提纯结构化数据           │
│     │   不可用时静默跳过                                   │
│     └─ 必应: 中文搜索，被拦截时自动切换英文重试           │
│         "{city} 必去景点" → "Beijing top attractions"    │
│                                                          │
│  3. 降级: DuckDuckGo (主搜索全部失败时)                   │
│                                                          │
│  4. 最终兜底: 高德 maps_text_search                      │
│     (DuckDuckGo 也不可用或未安装时)                       │
└─────────────────────────────────────────────────────────┘
```

### N2: `extract_attractions_node`

```
┌─────────────────────────────────────────────────────────┐
│  输入                                                    │
│  ├─ raw_search_results : str    # N1 的搜索结果文本      │
│  ├─ request.travel_days: int    # 用于计算提取上限       │
│  └─ request.preferences: list   # 影响景点类型筛选       │
├─────────────────────────────────────────────────────────┤
│  输出                                                    │
│  ├─ selected_pois : List[dict]  # 核心景点列表           │
│  │  每个元素: {"name": "故宫", "description": "..."}     │
│  └─ attractions_info : str (降级时) # 高德直接搜索结果   │
├─────────────────────────────────────────────────────────┤
│  内部逻辑                                                │
│  1. LLM 调用: 从 raw_search_results 中提取景点           │
│     max_count = travel_days × 3 (每天最多3个)            │
│     Prompt: EXTRACT_ATTRACTIONS_PROMPT                   │
│                                                          │
│  2. JSON 解析: _extract_json_from_llm_response()         │
│                                                          │
│  3. 数量不足时自动补充:                                   │
│     if len(valid_pois) < travel_days × 2:               │
│         调用高德 maps_text_search 补充景点                │
│         去重后追加到列表                                  │
│                                                          │
│  4. 完全失败时降级:                                       │
│     直接用高德搜索结果作为 attractions_info               │
│     (跳过后续的 geocode_attractions 节点)                │
└─────────────────────────────────────────────────────────┘
```

### N3: `geocode_attractions_node`

```
┌─────────────────────────────────────────────────────────┐
│  输入                                                    │
│  ├─ selected_pois : List[dict]  # N2 提取的景点列表      │
│  └─ request.city  : str         # 城市名                │
├─────────────────────────────────────────────────────────┤
│  输出                                                    │
│  └─ attractions_info : str      # 带坐标的景点详情文本   │
│     多个高德 API 返回结果的拼合                           │
├─────────────────────────────────────────────────────────┤
│  内部逻辑 (三层坐标获取策略)                              │
│                                                          │
│  对每个景点:                                              │
│  1. maps_text_search(keywords=景点名, city=城市)         │
│     → 获取 POI 列表，取第一个最佳匹配                     │
│                                                          │
│  2. maps_search_detail(id=POI的id)  ← 获取详细坐标       │
│     含: 经纬度、地址、电话、评分、门票                    │
│                                                          │
│  3. 名称去后缀重试:                                       │
│     "黄山风景名胜区" → 去掉"风景名胜区" → "黄山"          │
│     用简化名称重新搜索                                     │
│                                                          │
│  4. 失败的景点记录日志但继续处理其余景点                   │
│     单个景点失败不影响整体流程                             │
└─────────────────────────────────────────────────────────┘
```

### N8: `cluster_attractions_node` ⭐ 技术含量最高的节点

```
┌─────────────────────────────────────────────────────────┐
│  输入                                                    │
│  ├─ attractions_info : str    # N3 的景点坐标文本        │
│  ├─ request.travel_days: int  # 聚类目标组数             │
│  └─ request.free_text_input: str # 用户指定必游景点      │
├─────────────────────────────────────────────────────────┤
│  输出                                                    │
│  └─ cluster_info : str  # 格式化后的聚类文本             │
│     包含: 每日景点分组、组内TSP顺序、距离矩阵             │
├─────────────────────────────────────────────────────────┤
│  内部逻辑 (五步流水线)                                    │
│                                                          │
│  Step 1 — 坐标提取 (四层降级):                           │
│    ① 正则: 从 attractions_info 文本直接提取 name+坐标    │
│    ② maps_search_detail: 用 POI ID 查详细坐标           │
│    ③ maps_geo: 用景点名+城市名做地理编码                 │
│    ④ LLM: 让大模型从文本中提取 JSON 格式的坐标列表       │
│                                                          │
│  Step 2 — 距离矩阵构建:                                   │
│    ① maps_distance: 批量查询驾车距离 (高德 API)          │
│       - 对每个景点i，构建 destination=i，origins=其他     │
│       - 结果解析为 N×N 矩阵                               │
│    ② 缺失值补全: 用 Haversine 直线距离填充               │
│    ③ API不可用时: 全部用 Haversine 计算                  │
│                                                          │
│  Step 3 — K-Means++ 聚类:                                │
│    ① K-Means++ 初始化选种子点 (互相远离)                  │
│    ② 迭代分配-重算中心 (最多10轮)                        │
│    ③ 最大簇直径硬约束 (25km):                            │
│       簇内最远两点超过阈值 → 拆分远点分配到最近的其他簇   │
│                                                          │
│  Step 4 — TSP 最近邻排序:                                │
│    每个簇内用贪心最近邻排列游览顺序                        │
│                                                          │
│  Step 5 — 时长感知再平衡:                                 │
│    ① 估算每个景点的游玩时长 (从数据中提取或默认值)        │
│    ② 如果某天总时长 > 480分钟(8小时):                    │
│       把离质心最远的景点移到相邻的轻负荷天                │
│    ③ 最多迭代5轮                                         │
│                                                          │
│  Step 6 — 数量裁剪 (景点超过每天3个上限时):               │
│    ① 有用户指定必游景点: 保护必游，裁剪其余              │
│    ② 无必游: 选离聚类中心最近的 top-3                    │
│                                                          │
│  Step 7 — 逆地理编码补充地址:                             │
│    maps_regeocode: 用经纬度反查详细地址                  │
└─────────────────────────────────────────────────────────┘
```

```
              └──────┘ └─────┘ │ fallback   │
                               └─────┬──────┘
                                     │
                                ┌────▼──┐
                                │  END  │
                                └───────┘
```

### 4.2 子图节点详解

#### S1: `day_food_search_node`

```
┌─────────────────────────────────────────────────────────┐
│  与 N9 (search_food_node) 的区别:                         │
│  ① N9 通过 LLM 驱动工具调用 (间接)                        │
│     S1 直接调用高德 API (跳过 LLM)，更快更可靠             │
│  ② N9 搜整个城市的热门餐厅                                │
│     S1 只搜当天景点周边的餐厅，更精准                      │
│                                                          │
│  输入: 当天的 attraction_names, city, food_preference     │
│  输出: day_food_info (当天专属美食数据)                    │
│                                                          │
│  逻辑:                                                    │
│  for 每个景点 (最多3个):                                  │
│      在景点坐标周围2000米内搜索餐厅                        │
│  额外搜索城市热门菜系 (用于晚餐推荐)                       │
└─────────────────────────────────────────────────────────┘
```

#### S2: `day_plan_generator_node`

```
┌─────────────────────────────────────────────────────────┐
│  输入                                                    │
│  ├─ day_index, date, attraction_names, hotel_name       │
│  ├─ city, transportation, accommodation                 │
│  ├─ attractions_info, hotels_info, food_info (截断版)    │
│  ├─ weather_info, cluster_info                          │
│  └─ last_error (重试时携带上次错误信息)                   │
├─────────────────────────────────────────────────────────┤
│  输出                                                    │
│  └─ day_plan : DayPlan (单日完整行程)                    │
│     { date, day_index, description, transportation,     │
│       accommodation, hotel, attractions[], meals[],     │
│       route_segments[] }                                │
├─────────────────────────────────────────────────────────┤
│  逻辑                                                    │
│  1. LLM 调用 (DAY_PLAN_GENERATOR_PROMPT)                 │
│     - 要求景点名必须来自 attraction_names                  │
│     - 要求每个景点/餐厅的 location 有真实经纬度            │
│     - 要求早中晚三餐完整                                   │
│     - 不要求生成 route_segments (由 S3 自动生成)          │
│                                                          │
│  2. JSON 解析 + 默认值填充                                │
│     - date → 强制使用输入的 date                          │
│     - day_index → 强制使用输入的 day_index                │
│     - visit_duration → 默认120分钟                        │
│     - category → 默认"景点"                               │
│     - ticket_price → 默认0                                │
│                                                          │
│  3. 坐标校验 (_validate_plan_coordinates_single_day)      │
│     - 经纬度必须在 [73-136, 3-54] (中国范围)             │
│     - 超出范围的 location 置为 None                       │
│                                                          │
│  4. 失败时重置 retry_count 和 last_error，触发校验节点     │
└─────────────────────────────────────────────────────────┘
```

#### S3: `day_route_planner_node`

```
┌─────────────────────────────────────────────────────────┐
│  输入                                                    │
│  └─ day_plan (S2 的输出) + city + transportation        │
├─────────────────────────────────────────────────────────┤
│  输出                                                    │
│  └─ day_plan.route_segments : List[RouteSegment]        │
│     [{from_name, to_name, distance, duration, mode,     │
│       detail}, ...]                                      │
├─────────────────────────────────────────────────────────┤
│  逻辑 (按时间线构建路径点 → 逐段查询路线)                 │
│                                                          │
│  1. 构建时间线路径点序列:                                 │
│     酒店 → 早餐 → 景点1 → 景点2 → [午餐插入中间]         │
│     → 景点3 → 晚餐 → 酒店                                │
│                                                          │
│  2. 从搜索数据中模糊匹配每个路径点的坐标                   │
│     _find_coord() 五级匹配:                              │
│     精确匹配 → 子串匹配 → 去后缀匹配 → Jaccard相似度      │
│                                                          │
│  3. 逐段调用高德方向 API:                                 │
│     compute_route_segments():                            │
│     - 坐标过近(<10m): 跳过API，直接用步行估算             │
│     - 交通方式映射: "公共交通"→transit, "驾车"→driving   │
│     - QPS 限流: 自动等待 + 退避重试                      │
│     - API 失败: haversine 距离 + 速度估算兜底             │
│                                                          │
│  4. 将生成的 route_segments 写入 day_plan                │
└─────────────────────────────────────────────────────────┘
```

#### S4: `day_plan_validator_node`

```
┌─────────────────────────────────────────────────────────┐
│  校验规则:                                                │
│  ❌ day_plan 为 None                                     │
│  ❌ 景点列表为空                                          │
│  ❌ 餐数 < 3 (缺少 breakfast/lunch/dinner)               │
│  ❌ 路线段为空 且 有 ≥2个坐标点                           │
│  ❌ 任一景点的经纬度超出中国范围                           │
│                                                          │
│  任一规则不通过 → 设置 last_error，触发条件路由            │
│  全部通过 → 标记 done，子图结束                           │
└─────────────────────────────────────────────────────────┘
```

#### S5: `day_plan_fallback_node`

```
┌─────────────────────────────────────────────────────────┐
│  触发条件: S4 校验失败 且 retry_count ≥ max_retries(3)   │
│                                                          │
│  逻辑:                                                    │
│  1. 用 attraction_names 创建简易 Attraction 对象          │
│     (没有坐标、没有详情，只有名称)                         │
│  2. 从 day_food_info 中解析真实餐厅 (兜底用通用名)        │
│  3. 组装成最小可用的 DayPlan                              │
│                                                          │
│  设计理念: 宁可给出一个信息不完整的行程，也绝不返回空       │
└─────────────────────────────────────────────────────────┘
```

### 5.2 Reducer 机制：`day_plans` 的自动合并

```python
class TripPlannerState(TypedDict):
    day_plans: Annotated[List[dict], operator.add]  # ← Reducer
```

当 N 个 `day_plan_subgraph` 并行执行时，每个子图返回 `{"day_plans": [day1_result]}`、`{"day_plans": [day2_result]}`... LangGraph 的 Reducer 机制会自动将这些列表合并：`day1_result + day2_result + ...`。开发者不需要手动汇总。

### 7.1 中文搜索 → 英文自动重试

```python
# 必应搜索中文可能被内容审核拦截，自动切换英文重试
for attempt, q in enumerate(candidates):  # ["北京 必去景点", "Beijing top attractions"]
    try:
        result = await bing_service.search(query=q)
        break
    except Exception as e:
        if "content policy" in str(e) and attempt < len(candidates) - 1:
            continue  # 切换英文重试
```

### 7.2 JSON 六层容错链

```
LLM 输出 JSON 的解析策略 (parsing.py):

① Structured Output (function_calling)          ← 最可靠
     ↓ 失败/不支持
② 手动提取 JSON 块 (```json ... ```)             ← 常规路径
     ↓ 解析失败
③ _sanitize_json_str() 清理                      ← 去注释/去尾逗号/去控制字符
     ↓ 解析失败
④ _fix_unescaped_quotes() 修复引号               ← 修中文引号/未转义引号
     ↓ 解析失败
⑤ _repair_truncated_json() 补全截断              ← 补齐缺失的 }]}
     ↓ 解析失败
⑥ LLM 修复 (_llm_repair_json)                    ← 让LLM自己修自己的错误
     ↓ 仍失败
⑦ _create_fallback_plan() 硬编码降级              ← 最终兜底
```

## 八、面试时的"一句话讲透每个节点"

当被问到"你有哪些 Agent 节点"，用这个节奏回答：

> "我的系统被拆成 4 张 LangGraph 图，共约 27 个功能节点。最重要的几个是：
>
> **搜索层**：web_search_attractions 用小红书+必应+DuckDuckGo 三源聚合搜索攻略；extract_attractions 让 LLM 从攻略文本中提取景点名；geocode_attractions 用高德 API 把景点名转成经纬度坐标。
>
> **分析层**：cluster_attractions 是我自己写的 K-Means++ 地理聚类，加了 25km 直径约束和时长再平衡；macro_planner 让 LLM 生成一个极简的行程骨架（每天哪些景点、住哪个酒店），这个骨架大概 500 token，大幅降低了后续生成大型 JSON 的截断风险。
>
> **生成层**：最关键的是 day_plan_subgraph——我用 LangGraph 的 Send API 把骨架中的每一天并行派发给独立子图，每个子图内部有自己的美食搜索→详情生成→路线规划→校验→重试→降级循环。所有子图完成后 reduce_assemble 汇总合并。
>
> **收尾层**：global_synthesizer 生成行程标语和 Markdown 旅行建议；extract_preferences 和 save_preferences 从本次行程中自动学习用户偏好（酒店类型、菜系、景点类别），影响下次推荐。
>
> 另外还有一张 discovery_graph 用于交互式景点发现——搜出 20-40 个景点，每 5 个一批流式推给前端让用户选择。"
