# 预约信息、待办与日历提醒

景点预约信息现在可以从小红书攻略提取，经发现页、智能分日、草稿和对话替换传入最终行程。页面显示的是**攻略线索**，并未自动完成官方核验、查询余票或订票。

## 怎么使用

1. 重新搜索景点：景点卡片会显示“需关注预约”“预约信息待核实”或“预约规则有冲突”。展开“查看预约线索”，查看提前天数、放票时刻、渠道、原文、来源链接和采集时间。旧行程缺少这些数据时显示待核实，不会凭空补充。
2. 生成草稿：顶部新增“预约待办”。根据实际游览日期计算建议关注时间，展示尚未到关注时间、已到关注时间、待核实、已预约等状态。页面打开时每分钟刷新一次。
3. 自行完成预约后：点击“我已完成该日期的预约”，状态保存到草稿；支持撤销。定稿后在结果页的“预约待办”标签继续管理。
4. 需要手机/电脑日历提醒：点击“导出日历”，将 `.ics` 文件导入自己使用的日历，并开启该日历应用的通知。

示例：游览日期为 10 月 28 日，攻略明确写“提前 7 天、20:00 放票”，系统计算的关注时间为 10 月 21 日 20:00（北京时间）。这不是余票查询结果，也不是预约成功证明。

## 信息规则

| 数据情况 | 处理 |
| --- | --- |
| 攻略未提及预约 | unknown，待核实；不再默认“不需要预约” |
| 明确需要预约 | required；保留原文、渠道和来源 |
| 明确无需预约 | not_required，显示“攻略称无需预约，待核实” |
| 存在冲突或无法确定的条件 | conflicting；不据此计算确定的预约日期 |
| 模型给出原文中不存在的引文 | 丢弃预约结论，回到 unknown |
| 提前天数或时刻没有证据 | 清空结构化数值；保留可核实的文本线索 |

为避免编造日期，当前只自动计算原文中明确出现的“提前 N 天”（阿拉伯数字）；提前一周、特殊节假日、不同人群规则等复杂说法保留文本待核实。放票时刻需要原文中的明确 `HH:mm`。没有放票时刻但提前天数明确时，默认 **09:00 提醒**，页面和日历都注明这不是景点放票时间。

来源链接必须是搜索内容中已有的 HTTP(S) 链接，不能由模型补造；小红书笔记链接由搜索结果的笔记 ID 构建，不附带 Cookie 或签名 token。来源受平台登录与链接有效性影响，不保证无需登录即可打开。来源可能过时，始终提示用户向官方确认。

“已预约”与**具体景点和游览日期**绑定；重新选择其他景点或改变日期，不会继承为新预约。草稿标记与定稿保存均落到已有 JSON 数据中，无需新增数据库表。标记时检查数据是否已变化，避免覆盖并发编辑；已定稿草稿不可修改，应在最终行程中管理。

## 提醒范围

- 站内待办：打开页面时计算并刷新；未知信息也进入待核实清单。
- 日历导出：只导出有明确提前天数、未预约、游览日期未过且提醒时刻仍在未来的项目。已到时间的项目在站内提示尽快处理，不导出过时事件。
- 事件使用 UTC 时间，页面使用 Asia/Shanghai 展示，包含日历标准的 DISPLAY 提醒。日历客户端是否通知取决于导入方式、客户端和通知设置。
- 导出的文件是当时的快照。修改日期、景点或标记已预约后，需要在日历中清理旧提醒并按需重新导入；当前没有日历订阅同步。
- 本轮没有后台短信、邮件、微信推送，也不会自动打开预约网站或代订门票。

## 接口和实现

`kind` 为 `draft` 或 `trip`，`id` 是草稿 ID 或已保存行程 ID：

| 接口 | 用途 |
| --- | --- |
| GET `/api/reservations/{kind}/{id}` | 返回按北京时间计算的预约待办 |
| PATCH `/api/reservations/{kind}/{id}/{task_id}` | `{ "booked": true }` 确认已预约，false 撤销；必须是布尔值 |
| GET `/api/reservations/{kind}/{id}/calendar.ics` | 导出符合条件的日历事件 |

核心文件：`backend/app/models/reservation.py`、`services/reservation_extraction.py`、`services/reservations.py`，以及前端 `ReservationNotice.vue` 和 `ReservationChecklist.vue`。保留 `reservation_required` / `reservation_tips` 兼容旧页面，新数据统一存入 `reservation` 对象；旧数据的 false 默认值按“未知”处理。

规划校验新增预约待办与规则冲突的警告，不因用户还未预约就阻止保存旅行计划。旧版模型直接生成流程会重新绑定来源中的预约字段，不能让模型自行声称用户已经预约。

## 验证和演示

在 backend 目录执行：

```powershell
python -m pytest tests/services/test_reservations.py -q
python -m pytest -q
python scripts/demo_upgrade.py
```

前端启动方法见 [升级说明](agent-upgrade.md)。离线演示的日期自动设为当前北京时间两周后，第一天包含合成的预约规则；可直接演示下载日历、标记已预约、刷新、定稿和撤销。第二天替换为室内景点后会出现新的预约待办。所有演示规则都标明为合成数据，不代表对应真实景点。

测试覆盖来源 URL/原文保留、JSON 中 URL 与嵌套数组解析、发现与地理编码、智能分日、草稿和定稿传递、未知/冲突状态、预约日期与时区、状态持久化、日历中文折行与注入字符转义。真实小红书 Cookie、外部模型提取质量和各日历客户端通知行为需要在真实服务环境中另行验证。
